# Email workspace UX evidence and proposed study

Reviewed: 2026-11-03. This is desk research and a study protocol, **not participant research or proof that our redesign is better**. No participant was recruited, mailbox accessed or result collected. Public feedback is paraphrased without copying user identifiers or personal examples.

## Evidence levels

- **Published empirical research:** studies support bounded claims about their populations/methods, not causation for this product. Confidence concerns the source finding; transfer confidence is separately limited.
- **Official product documentation:** high confidence that the documented pattern/capability exists, conditional on version/eligibility. This is not independent usability research.
- **Anecdotal feedback:** individual self-selected reports identify potential problems, not prevalence or representative preference.
- **Product hypotheses:** our proposed design choices need evaluation. Engineering tests establish functionality, not user benefit.

## Design hypotheses and visible changes

| Hypothesis                                   | Existing surface                                          | Revised surface                                                                           | Evidence needed                                                         |
| -------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Familiar task entry reduces orientation cost | /app opens analytics Overview; Inbox is a separate action | /app defaults to Inbox, with Overview retained at /app/overview and selectable as default | First-click/task success and interview explanation                      |
| Search is easier to discover                 | Search appears only inside Inbox                          | Persistent header search, optional / focus shortcut and honest syntax help                | Search discovery time/errors; do not infer benefit from placement alone |
| Rows aid scanning                            | Avatar/card-like vertical message presentation            | Sender, subject/preview, category/priority, date and explicit read/unread semantics       | Find-message success, scan errors and density preference                |
| Optional context reduces navigation burden   | Native modal reading                                      | Dialog default plus optional side pane at >=1100px; dialog fallback on smaller widths     | Matched read/return tasks; viewport and keyboard differences            |
| User control reduces mismatch                | One fixed display/default view                            | Separate local density/layout/default controls without changing onboarding                | Preference comprehension, reload/reset and self-reported control        |

These are structural before/after observations, not measured usability improvements. The current Inbox contains all loaded messages, not only Gmail INBOX-labeled mail; it remains an explicitly partial sample in live mode. No archive/read-state write, conversation grouping, complete reader or sending is implemented.

## Proposed small comparative study — not executed

**Question:** Does an inbox-first surface improve common discovery/inspection tasks without reducing source/privacy comprehension compared with the existing Clario dashboard?

**Recruitment:** Aim for 6–8 adults who voluntarily use email at least weekly; include regular Gmail users, some users of Outlook/other clients, varied task volumes, and keyboard/assistive-technology users where feasible. Start with acquaintances/opt-in community recruitment after owner approval. Do not scrape contacts, access accounts, require a role declaration or promise payment/budget. Record only a coarse optional experience band, not employer/address/mailbox contents. Small purposive sampling supports formative findings, not statistical representativeness.

**Materials:** Separate local builds of the preserved baseline and revised UI; the same 96 synthetic message corpus, source labels and disabled real network. Alternate equivalent task targets to reduce memorization. Both variants use mock data only; the researcher supplies fake auth outcomes for connection tasks. Capture the build/version/viewport and test condition, never real messages or tokens.

**Protocol:** 35–45 minute moderated within-participant comparison. Obtain informed consent; explain voluntary withdrawal and that the interface, not the person, is under test. Counterbalance A→B/B→A and task-target sets. Give an equal short introduction; initial tasks use each variant's default, later density/pane tasks use explicit controls. Use think-aloud for qualitative diagnosis but interpret timing cautiously because narration changes task time. Separate first-attempt unaided timing from later coaching. Record failures/help as outcomes; no silently discarded trials.

**Tasks:**

1. Find a synthetic interview invitation using sender/subject search; explain whether search covers the entire real mailbox.
2. Combine Jobs and internships + High priority, inspect a classification reason and return to the same result list.
3. Identify an unread message and explain whether opening changes Gmail read state (it does not here).
4. Compare two messages using available reading layouts; return focus to the list. Baseline may require repeated modal use; record actions, not assumed superiority.
5. Find a recurring sender/category insight without losing search context; return to Inbox.
6. Change density and default workspace where supported; distinguish an unavailable baseline feature from a failed task. Only shared tasks enter paired timing comparisons.
7. Skip/restart optional onboarding and clear **display** settings while retaining declared goals; explain the two preference purposes.
8. Use fake Connect/Authorize/Disconnect; identify read-only scope, metadata-only/sample limits and what persists. No real Google interaction.
9. With narrow viewport/keyboard, search/open/close a message and recover from empty results.

**Metrics and collection:**

| Measure                 | Definition / collection                                                                    | Interpretation                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Unaided task success    | Correct target/action + required explanation before hint / attempts                        | Separate functional completion and privacy comprehension                             |
| Time on common task     | Stopwatch from task reveal to correct completion; retain failures/censoring                | Paired medians/ranges; no tiny-sample significance or general speed claim            |
| Interaction/error count | Researcher checklist of navigation, wrong targets, missed focus and reset/recovery         | More clicks are not automatically worse; classify severity/context                   |
| Subjective effort       | Post-task 1–7 single ease question plus explanation                                        | Descriptive self-report; do not turn ordinal ratings into precise productivity gains |
| Retained context        | Correct query/filter/selected message identification after reading or analytics navigation | Account for layout differences and unsupported baseline features                     |
| Privacy comprehension   | Correctly state sample coverage, no mark-as-read, session mail vs stored preferences       | Critical safety gate, not just satisfaction                                          |
| Control/preference      | Chosen density/layout and reasons                                                          | Preference is not task-performance proof                                             |
| Accessibility issues    | Focus loss, inaccessible names, overflow and assistance required by viewport/input mode    | Review each serious issue; no certification from a small sample                      |

**Proposed success gates (targets, not results):** At least 80% unaided success on common search/filter/read-return tasks, zero critical misunderstanding that messages were sent/deleted/marked read, and at least 80% correct sample/storage/scope comprehension. Revised shared-task medians should not materially regress (investigate >10% descriptive slowdown); record uncertainty/participant variation rather than declaring superiority. Every blocking keyboard issue must be fixed before broader use. Thresholds are initial decision rules, not validated baselines or power calculations.

**Interview prompts:** What did you expect on opening the app? Which row information mattered first? What did “Inbox” and “Unread” mean here? Did the side pane help or crowd the list? Which setting would you keep? Where would you look for a thread summary or reply? What should require permission? What data did you think would survive reload? When did classification evidence help or distract? What would make you distrust an AI summary?

**Analysis and privacy:** Use anonymous session IDs and aggregate task counts. Obtain separate permission for recording; default to researcher notes on synthetic tasks, no real desktop/account capture. Store notes locally under an owner-approved retention period (proposed 30 days), allow withdrawal/deletion, avoid external AI transcription and do not commit notes. Code themes with supporting observations; retain disconfirming cases and publish only anonymized aggregates. No recruitment, recording, data collection or participant results exist yet.
