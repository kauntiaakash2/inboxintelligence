# Domain and storage model

The TypeScript contract is `src/domain/models.ts`. Existing source fields below are implemented unless explicitly marked planned. Default instances are synthetic; optional Gmail instances are real after explicit authorization, while automated tests use only fake Gmail data; privacy classifications describe real equivalents. Message IDs and history IDs are strings: never parse provider IDs into JavaScript numbers.

| Model                | Fields and meaning                                                                                                                                                  | Relationships / indexes                                                                                                | Privacy classification                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| EmailMessage         | id opaque message ID; sender normalized object; subject/snippet text; receivedAt ISO instant; labels provider labels; unread derived flag; body optional plain text | Account+id future primary key; sender.id, receivedAt, category and unread indexes; body not indexed                    | Highly sensitive correspondence; metadata also personal                |
| EmailSender          | id stable normalized sender identity; name display text; address mailbox address                                                                                    | Referenced by message.sender and SenderPattern.senderId; account+normalized address unique                             | Personal contact data; do not export in telemetry                      |
| EmailCategory        | Literal union: Personal, Jobs and internships, Education, Finance, Security, Orders, Promotions, Newsletters, Events and deadlines, Spam review, Uncategorized      | Current stable names act as IDs; future renameable categories need separate stable IDs                                 | Low sensitivity alone; membership reveals interests                    |
| ClassificationResult | category; confidence [0,.95]; reason; optional ruleId; priority High/Medium/Low; priorityScore [0,100]; novel unmatched flag                                        | One per ClassifiedMessage; future include rule version and evaluation provenance                                       | Derived personal profiling; local-only                                 |
| SenderPattern        | senderId; category; count; lastSeenAt; version                                                                                                                      | Planned persistence; compound account+senderId and lastSeenAt                                                          | Behavioral profile, sensitive                                          |
| ClassificationRule   | id; category; keywords; optional senderDomain/label; priority                                                                                                       | Ordered rules; id used in explanation; future versions immutable                                                       | Usually configuration; custom rules may contain personal patterns      |
| UserCorrection       | id; messageId; previous/corrected category; timestamp                                                                                                               | Planned; compound account+messageId, timestamp; validate categories                                                    | Sensitive user preference/profile                                      |
| SyncCheckpoint       | accountId; optional historyId/pageToken; updatedAt; schemaVersion                                                                                                   | Planned one per account+coverage/job type; persist atomically after upserts                                            | Sensitive linkage/state; page tokens not telemetry                     |
| SyncJob              | id; status idle/running/completed/failed; startedAt; optional completedAt; indexed/failed counts                                                                    | Planned durable job ledger; account+startedAt/status indexes; needs explicit account association before implementation | Operational metadata; opaque IDs                                       |
| MetricEvent          | name union; timestamp numeric epoch ms; source synthetic/real; jobId; optional durationMs                                                                           | Implemented bounded session buffer, no persistence; future index by source/name/time                                   | Operational; content-free but potentially linkable, minimize retention |

`EmailRepository.list()` returns a Promise of normalized messages. `Instrumentation.track/snapshot` is the event interface. The UI never consumes Gmail JSON. `ClassifiedMessage` joins message and classification, avoiding duplicated category fields.

## Planned schema evolution

Before IndexedDB implement account-scoped keys across every table; current synthetic IDs are not multi-account safe. Separate messages, senders, rules, corrections, jobs and checkpoints with versioned migrations. Store stable Gmail message IDs and opaque history IDs; thread IDs and hydration-depth flags belong in the future adapter model. Persist provider deletion tombstones or remove messages according to retention policy. Unique upserts make replay idempotent.

Use compound indexes for account+date and account+category+date where real access patterns justify them. Full-text search needs a considered local index; current substring scan is appropriate for 96 and initially fewer than 5,000 messages. Do not index bodies by default. Browser storage is origin-isolated, not encrypted against malicious same-origin scripts or device users. Delete all account-related stores transactionally and document export handling. Validate unknown JSON before trusting static types; current validator covers required fields, dates, labels, unique IDs, sender shapes and optional body type.

## Phase 2 normalization and ephemeral state

EmailMessage.id is the Gmail message ID; sender identity lowercases a validated mailbox address; display name/address remain untrusted text. Missing/unparseable From yields name Unknown sender, address empty string and an isolated `unknown:<messageId>` sender key. No fake address is invented. Subject defaults to (No subject). receivedAt derives from numeric-string internalDate converted to a valid ISO instant; Date header does not override Gmail ordering. labels are provider label IDs (not custom display names); unread comes from UNREAD.

Gmail snippets are deliberately not requested, so snippet is empty in live mode and body is absent. This keeps the established UI/domain contract while minimizing content retrieval. Source is tracked by the mailbox session rather than embedded in provider records. Shared validateMessages moved to src/domain/validateMessages.ts; mockEmailRepository re-exports it for compatibility. An empty sender address now explicitly means unavailable; other malformed addresses remain rejected.

GmailCoverage: discovered = unique selected IDs (maximum 100), loaded = successfully validated metadata, failed = skipped invalid/unavailable messages, hasMore = remaining list page indicated, excludesSpamTrash = true. GmailProgress: discovery/metadata phase plus completed/total. These contain no IDs/content and are not persisted. Counts are not authoritative mailbox totals.

AuthorizationState exposes status, content-free message and version only. Token/expiry remain in private service fields. MailboxResult stores classified messages, safe error, event snapshot and coverage for one source/session key. Disconnect/expiration clears it; late request results are discarded. User selection stores only an ID/session key, avoiding a second retained message object. No IndexedDB schema or OAuth credential table was implemented.

GmailRequestDiagnostics contains requestAttempts, listAttempts, metadataAttempts and retries (all numeric counts). MailboxResult also has nullable diagnostics/durationMs; neither is persisted. No URL, message identifier, credential, account reference or content field belongs in diagnostics. Retained live-record count is derived from the actual stored result source, including during cleanup, not merely the visible row list.

## Phase 3A implemented preference schema

`src/domain/preferences.ts` adds `UserPreferences`, independent of EmailMessage and account identity. One record is keyed by the constant `inbox-intelligence.preferences`; it needs no secondary indexes.

| Field             | Meaning and validation                                                              | Privacy                                        |
| ----------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------- |
| schemaVersion     | Literal 1; unsupported versions ignored, explicit future migration required         | Configuration                                  |
| status            | completed or skipped                                                                | Declared setup state                           |
| profile           | null or student/professional/freelancer/general/prefer-not-to-say                   | Optional user-declared context, never inferred |
| goals             | Unique enum array: important/deadlines/career/clutter/patterns/finance              | Declared interests, potentially personal       |
| enabledCategories | Unique existing EmailCategory IDs, subset of current recommendations; all-off valid | Declared presentation preference               |

An exact key allowlist rejects extra data. Skipped means null profile and empty arrays. Loaded/saved objects are copied and canonicalized using the deterministic goal/category mapping. No timestamps, stable user/device ID, account ID, message references, sender identifiers, credentials or free text belong here. `PreferenceDraft` omits version/status and exists only while the form is open. Step state is a 1|2|3 union, not a persisted processing percentage.

Preferences have no relationship/foreign key to Gmail or classification records. The current category literal names remain their IDs; rename migration must be designed before changing them. Reset deletes this key only; unavailable storage falls back to tab state with a notice. Future device portability requires explicit validated export/import or a reviewed authenticated profile service; no such service exists. Mail caching and account-scoped schema evolution above remain planned.

## Workspace display preferences — separate implemented record

Key inbox-intelligence.workspace stores exactly schemaVersion (2), sidebarState (expanded|collapsed), density (comfortable|compact), readingLayout (dialog|split), defaultView (Inbox explorer|Overview|Analytics). These are user-declared UI enums without relationships to account, message, sender, profile/goals or token records. No secondary indexes are needed. Load caps serialized input at 1024 characters, rejects extra fields/unsupported versions, and falls back safely; explicit reset removes only this key. No migration or format change was made to inbox-intelligence.preferences.

The current EmailMessage still lacks a persisted thread/content hydration model. Planned full-reader models must add validated threadId, selected MIME text/coverage/error state and account/session-bound retrieval provenance separately. AI evidence must point to validated source records/spans without placing IDs in public URLs. Sending drafts and outbox state require separate privacy/schema decisions; none is stored now.

Display v1 migrates in memory to v2 by preserving density, layout and default view and adding expanded sidebar state. Both versions require their exact field allowlists. Migration/load never writes; the next explicit display save serializes v2. Unknown versions or invalid sidebar states fall back safely. Reset removes only the display key. Mobile drawer open/closed state is not persisted. The original onboarding schema remains v1 and unchanged.
